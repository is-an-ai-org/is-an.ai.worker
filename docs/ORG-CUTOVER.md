# 컷오버 순서 — 다운타임 최소화

## 0. 지금 무엇이 죽어 있고 무엇이 살아 있나

이 구분이 순서를 전부 결정한다.

| 경로 | 상태 | 근거 |
|---|---|---|
| **기존 도메인 조회 (읽기)** | ✅ **살아 있다** | 히든 마스터 + HE 세컨더리 5대. org와 무관하게 계속 응답한다 |
| **신규 등록·수정·삭제 (쓰기)** | ❌ 이미 죽어 있다 | org flagged → Actions 중단 → 파이프라인 단절 |

그래서 **"다운타임 최소화"의 목표는 복구를 빨리 하는 게 아니다.**
쓰기는 이미 죽어 있어서 몇 시간 더 걸려도 추가 손해가 없다.
목표는 **살아 있는 읽기 경로를 이전 과정에서 죽이지 않는 것**이다.

## 1. 진행도 (2026-08-25 실측)

| 태스크 | 상태 |
|---|---|
| B-01 새 org `is-an-ai-org` 생성 | ✅ 완료 |
| B-02 App transfer 가능 여부 | ✅ 확인 — **불가능**. App 재생성 경로 확정 |
| B-03 이후 전부 | ❌ 미착수 |

로컬 5개 레포의 remote는 **전부 아직 `github.com/is-an-ai/`** 를 가리킨다.
새 org로 옮겨진 것은 아무것도 없다. 되돌릴 것도 없는 상태다.

## 2. 진짜 위험은 이전이 아니라 전체 동기화다

`sync-pdns-dns`는 **"레포에 없으면 PowerDNS에서 지운다"** 는 전체 동기화이고
매일 **02:00 UTC(한국 11:00)** 에 돈다. 보호 대상은 `ns1`/`ns2`/`_vercel` 같은
인프라 레코드뿐이라, 사용자 레코드 3,675건에는 가드가 없었다.

**레포가 불완전한 상태에서 이게 한 번만 돌면 존이 비고 HE까지 전파된다.**
발생 경로가 실재한다:
- `schedule` 이벤트는 **기본 브랜치**를 체크아웃한다 (작업 브랜치가 아니다)
- org 이전 중 부분 푸시 상태에서 cron 시각을 넘기는 경우
- 체크아웃 실패

→ 레코드 레포 브랜치 `fix/bulk-delete-guard`에 가드를 넣었다.
삭제가 **50건 초과 AND 전체의 5% 초과**면 `exit 1`.
의도한 악용 56건 정리(1.5%)는 그대로 통과하고, 절반 푸시(49%)·빈 레포(100%)는 막힌다.
**이 가드를 먼저 머지하고 이전을 시작한다.**

## 3. 순서 원칙 세 개

1. **읽기 경로(PowerDNS·HE)는 이전 내내 손대지 않는다.** 존을 건드리는 유일한 것은 동기화뿐이고, 그건 꺼둔다.
2. **쓰기 경로는 반쯤 연결된 상태를 만들지 않는다.** 완전히 구 org이거나 완전히 새 org다.
3. **되돌릴 수 없는 것을 마지막에 한다.** 구 레포 archive는 검증이 끝난 뒤다.

## 4. 단계

### Phase 0 — 안전장치 (다운타임 0, 이전 전에 반드시)
1. `fix/bulk-delete-guard` 머지
2. **존 백업**: `dig AXFR @<master> is-an.ai > zone-backup.txt` — 되돌릴 수 있는 유일한 수단
3. D1 export + 레코드 레포 bare clone + 서버 설정 tar
4. **새 레포에 올릴 커밋에서는 `sync-pdns-dns.yml`의 cron을 주석 처리해 둔다.**
   push하는 순간 새 org에서 스케줄이 살아나기 때문이다. 검증 끝나고 다시 켠다.

### Phase 1 — 새 org 준비 (다운타임 0, 구 경로 그대로)
5. 새 org에 레포 생성 — **이름은 그대로**(`is-an.ai` 등). 워크플로 경로에 박혀 있다
6. 삭제 목록 확정 (B-04 검토 시트 56건부터)
7. 삭제 적용 + **히스토리 없는 초기 커밋** + push (cron OFF 상태)
8. 파일 수 대조: `원래 3,675 − 삭제 수`

이 시점까지 러너는 구 org에 그대로다. **아무 일도 일어나지 않는다.**

### Phase 2 — App 재생성 (다운타임 0)
9. GitHub App 새로 생성 → App ID / private key / installation ID
10. **새 봇 이메일 확인** — 추측하지 말 것. 새 org에서 App이 만든 커밋 하나의 author를 본다

### Phase 3 — 컷오버 (여기만 쓰기 경로가 움직인다)

**러너를 워커보다 먼저** 옮긴다. 순서를 뒤집으면 안 되는 이유:
- 워커 먼저 → 커밋은 새 레포에 들어가는데 러너가 구 org에 있어 Actions가 안 돈다.
  등록 API는 201을 반환하는데 DNS에는 반영되지 않는 **유령 상태**가 된다.
- 러너 먼저 → 새 레포는 이미 완전하고 cron은 꺼져 있어 아무 일도 안 한다. 워커는 아직
  구 org에 커밋하는데, 그건 지금도 반영 안 되는 상태라 **나빠지는 게 없다.**

11. 러너 재등록 (구 org 제거 → 새 org 등록). `Idle` 확인
12. 새 org에 secrets 입력 — `PDNS_API_KEY`, `PDNS_ZONE`, App secret 3종
13. **⭐ `workflow_dispatch`로 sync를 `dry_run=true`로 1회 실행**
    이게 결정적인 관문이다. 적용 없이 "무엇을 지울 것인가"만 본다.
    - 삭제 예정 = 의도한 삭제 목록과 일치 → 진행
    - 수천 건 → **즉시 중단.** 레포 푸시가 불완전하다
14. 워커 `wrangler.jsonc` 네 값 교체 후 배포 — **쓰기 경로가 여기서 넘어간다. 소요 1~2분**
15. 검증 6단계: 테스트 등록 → 새 레포 커밋 → D1 → Actions → PowerDNS → `dig @ns1.he.net`.
    삭제 경로까지 확인

### Phase 4 — 정리 (검증 통과 후에만)
16. sync cron 다시 켜고 `dry_run=false`로 1회 수동 실행 → 삭제 목록이 존에 반영됨
17. 삭제 건 전건 `dig @ns1.he.net` → **NXDOMAIN 확인**.
    TTL이 300초라 최대 5분 늦게 사라진다
18. 구 레포 **private 전환 후 archive** (삭제하지 않는다)
19. 24시간 뒤 새 org 상태 확인 ← 여기서 처음으로 flagged 사유 가설의 답을 얻는다

## 5. 다운타임 정산

| 대상 | 추가 다운타임 |
|---|---|
| 기존 도메인 조회 | **0초** — 읽기 경로를 건드리지 않는다 |
| 신규 등록 | 이미 다운. 14번에서 복구. 추가분은 **워커 배포 1~2분** |
| 삭제한 악용 도메인 | 의도된 것. TTL 300초만큼 늦게 사라진다 |

## 6. 롤백

Phase 3 어디서든 되돌릴 수 있다. 존을 안 건드렸기 때문이다.
1. 워커 `wrangler.jsonc`를 구 값으로 되돌리고 배포 (1~2분)
2. 러너를 구 org로 재등록
3. 그래도 존이 손상됐다면 Phase 0-2의 AXFR 백업으로 복구

**Phase 4의 18번(archive)을 하고 나면 롤백이 어려워진다.** 그래서 마지막이다.

## 7. 절대 하지 말 것

- `JWT_PRIVATE_KEY` / `JWT_PUBLIC_KEY` 로테이트 → 전 사용자 강제 로그아웃.
  도메인 소유권은 D1 `providerId`로 유지되므로 OAuth App을 새로 만들어도 재로그인이면 된다
- 러너를 없애고 워커가 PowerDNS를 직접 호출 → PDNS 주소가 노출되어 히든 마스터가 깨진다
- 같은 날 PowerDNS 재시작 → 장애 원인이 org 이전과 갈린다
- 13번(dry run) 건너뛰기 → 이 순서에서 유일하게 존을 지울 수 있는 지점이다
